advc — language reference

Reference: save migration (advc save-migration)

A save file stores where each thread is parked — a block of a function. When you ship a new version of a game, the blocks of an edited function change, so a save made by the old version can point into code that no longer exists. advc save-migration compares two released versions and writes a file proposing, for every saved position of the old version, where it should resume in the new one.

The compiler reads these files: a game built with a migrations/ folder carries the migration inside it, and a save made by an older build is carried across when it is loaded (see Using the file).

Usage

Run it inside the game folder, which must be inside a git repository:

cd tests/crime-scene
advc save-migration v1.0 v1.1

<from> and <to> are any git commit-ish: a tag (v1.0, crime-scene/v1.0), a branch, or a sha. A / in a ref becomes _ in file names.

For each ref the command makes a temporary git worktree that checks out only the game folder, compiles it with the current compiler up to the control flow graphs (no LLVM build, no link), and keeps a snapshot under target/save-migrations/<ref>/. The worktree is always removed afterwards.

It then writes migrations/<from>.<to>.advm in the game folder and prints a summary:

wrote migrations/v1.0.v1.1.advm (1 unit(s), 1 proposed row(s), 1 needing a decision, 1 kept from the previous file)

Running the command again is safe: the file is merged, not overwritten. Only the remap rows are yours — the from line, the sections and their comments always come from the fresh diff:

  • A row where you replaced the ? (a decision) survives, in the fresh proposal’s place; the comment you wrote rides along. A row you added for a block the diff proposes none for survives too, in its function’s section (a section is added for a function the fresh file has none for).
  • A decided row whose block or target no longer exists in the fresh diff (the code changed under it, the old ref moved, the function was removed) is commented out as // <your row> // [GONE] <why> — the block then falls back to its default, or the build asks for a row, and you decide again. The report counts them: N marked [GONE].
  • A ? row you left undecided regenerates with today’s candidates; a proposal you deleted comes back. An untouched file is rewritten byte for byte.

What the merge cannot tell: whether a kept decision is still right. If the fresh diff has changed underneath it and the target still exists, your row stays — read the [GONE] marks and re-run before re-committing the file.

The .advm file

The file holds only what you may need to decide: the from line naming the two builds by their build id, and remap rows, each under the section of the function it is about. Everything else is a comment for you to read. Example for a game where two lines of a dialogue swapped places:

from 3f2a9c…64 hex chars… -> 8d41b7…64 hex chars…

// main.advf
// func optWhat
//    func optWhat
//        crime::askedWhat = 1   // b0 = a0
//        wait sequence
//            talk AskWhat       // b1 = a1
//  -         talk OffWhat1      // b2
//  -         talk OffWhat2      // b3
//  +         talk OffWhat2      // a2
//  +         talk OffWhat1      // a3
//            talk What3         // b4 = a4
//        end                    // b5 = a5
//        crime::talking = 0     // b6 = a6
remap b2 to a2 // proposed
remap b3 to ? // proposed candidates: a2, a4
  • from <build id> -> <build id>. The two builds, each named by its build id: a hash of the game’s source (every .advf it reads, with comments and blank lines ignored) and of the names of the files in assets/. A save records the id of the build that wrote it; this is how the game knows which saves the file applies to. No git tag or commit is written in the file (the file name keeps the refs you typed). Edit a comment, add a blank line, commit the file or anything else in the repository, and the id stays the same; change the game and it changes.
  • Section header. The file the function lives in (relative to the game folder), then // func <name>. A renamed function reads // func old → new; a removed one is tagged // func <name> [REMOVED]. The rows below a header are about that function. (Do not write a // func … line of your own: it would start a new section.)
  • The diff. The function’s source, with the block ids on each line. bN is block number N of the function in the first ref, aM block number M in the second. A removed line (-) shows only its bN, an added line (+) only its aM. On an unchanged line, bN = aM is the default: where a save parked at bN resumes when no row says otherwise. On a line that reads b1,b2 = a1,a2 · a4,a5, the defaults of this line’s old blocks are on another line, and a4,a5 are the new blocks on this one. The ids belong to this one comparison.
  • Rows. remap bN to aM // proposed says “a save parked at old block bN should resume at new block aM”, overriding the default for that block. remap bN to none means the thread ends there.
Old positionWritten as
resumes at its default (unchanged, moved, or only its literals changed — a retyped subtitle, another volume or duration)nothing
resumes at a different new blockremap bN to aM // proposed
has no counterpart, the surviving block down its chain is foundremap bN to aM // proposed
has no counterpart, nothing followsremap bN to none // proposed
ambiguousremap bN to ? // proposed candidates: … — a live row whose ? target must be replaced by hand; until then the file is not valid

Nothing for you to do means nothing in the file. Where each function’s blocks sit in each build, which functions moved because an earlier one grew, which were renamed or removed, and every block’s default are not written: the build recomputes them from the two builds on the from line. A function that only moved, or changed only in literals, has no section; a removed function’s threads end, so it has a section (to tell you) but no rows; new functions have no old positions and do not appear.

Using the file

The file does nothing until a build includes it. The workflow:

  1. Tag the version you shipped (v1.0) and the one you are about to ship (v1.1).
  2. advc save-migration v1.0 v1.1 writes migrations/v1.0.v1.1.advm.
  3. Review it. Every remap … to ? is a position the tool could not decide: pick one of the candidates (or none) and replace the ?. You may also change any other row.
  4. Commit it and build the game. Committing the file does not change the build, so the build of the commit that ships it is the build the file names. The build embeds every migrations/*.advm: it finds the sources of both builds of each file (only the game folder), recomputes the same comparison, applies your rows, and turns the result into a table from old dispatch ids to new ones, so the shipped game carries its own migrations. Each build is found by its id: first among the snapshots cached under target/save-migrations/ (the ones advc save-migration made are reused), and on a fresh clone, where there are none, by searching the game folder’s git history for the commit that builds to that id. The build therefore needs the repository’s history (not a shallow clone), and the first build after a clone takes longer.

When a save is loaded, the game compares the build id the save was written with to its own. A release that only touched comments is the same build, so its older saves load with no file at all. If they differ and the game ships a chain of migrations from that build to this one (1.0 → 1.1 → 1.2 chains), every position the save holds — each parked thread, each timer, each saved function reference — is carried across it. Otherwise the load is refused: a save from a build the game has no migration from (or one that does not say which build wrote it) is not loaded wrong; it is not loaded at all. The game keeps running exactly as it was, and the reason is printed ([load] FAILED, nothing was loaded: …, naming both build ids). In a stdin script, a refused load fails the script with exit status 1. Every other failure to load — a missing file, a file that is not a save, a truncated one — is the same: nothing is loaded, nothing changes.

The build fails when a file cannot be used, listing each problem with its line: a ? still waiting for a decision, a block number that does not exist, a section that does not match the recomputed comparison (the file is stale), an old block with no counterpart and no row, a line that does not parse. It only warns when no file in migrations/ leads to the build being compiled (saves from older builds are then refused): the usual cause is that the sources changed after the migration was generated — run advc save-migration again for the version you are building. Every build has an id, whether or not the game folder is a clean git checkout: uncommitted changes change the id like any other edit to the sources, and nothing else about git does.

Spoken lines in flight

A talk <voice> line playing at the moment of a save is not a position to remap. The game keeps each line as one unit — its subtitle, its lip-sync, its recording and the thread waiting for it all end together — and the save stores that unit whole, with the text it was showing. When the new version loads the save it checks the line against the new build: the same recording (same length and sample rate), the same lip-sync animation, the speaking actor still there. If it all matches, the line carries on from where it was. If anything changed — the recording was replaced or removed, the lip-sync was regenerated — the line is dropped as if it had just finished: no subtitle, no sound, and the story continues past it. A line is never replayed half-changed, and it never leaves the game waiting for a recording that is gone.

So a retyped subtitle (the old text finishes over the old recording) and a replaced recording (the line ends at once) both need nothing from this file. A re-recorded line with exactly the same length and sample rate is not noticed as changed.

Limits

  • The current compiler compiles both refs. A grammar change since an old tag can make it fail, or lower differently.
  • A game’s assets/ must be tracked in git at both refs.
  • Animation units are skipped: an animation slot saves a frame index, not a block position.
  • Only the positions are migrated. The table carries where each parked thread is and which function each saved reference points at. The other things a save holds by number — variables, actors, assets, animations, strings, items — are numbered per build and are not translated, so a save across two builds that add or remove any of them can still load those wrongly. (A save the game cannot vouch for at all — no migration from its build — is refused instead.)
  • A save is migrated only if it was written by a build that records a build id (this feature’s builds and later). An older save has none, so a game refuses it. The refusal is a message on the console; the player is not told in the game yet.
  • The .advm must be generated for the sources being built. The migration refers to the blocks of the <to> build; edit the code afterwards and the build’s id changes, so no file leads to it.
  • The id is a function of the source, not of the compiler: a compiler update that lowers the same source differently is not noticed.
  • Not carried across yet: nothing of thread/handler positions — since 2026-11-13 the open UI trees (2.1) and the when-arm units and UI builders (2.2) carry through the table too. The save’s other numbers (variables, actors, assets, animation indexes) are per-build still (stage 3).
