advc — language reference

Overview

advc is a compiler for narrative games. You write your game in a small, friendly language called advc, and one command turns your source files into a finished, playable game.

What kinds of games?

advc covers the classic narrative genres:

  • Point-and-click adventures — painted rooms, characters that walk, inventory items, puzzles, verbs like Look / Pick / Talk to.
  • Gamebooks (choose-your-adventure) — page-based stories where every paragraph offers choices that lead somewhere else.
  • Visual novels — dialogue-driven scenes with choices, sprites, and routes that converge on several endings.
  • Puzzle and life-simulation hybrids — weekly planners, timers, score tracking, any game where what matters is the state and the choices.

If your game is mostly places, characters, dialogue, choices and state, it is an advc game.

Why a specialized language?

Every one of those games is built from the same small set of ideas: a scene, a character standing somewhere, a line of dialogue, a choice offered to the player, an item picked up, a puzzle that depends on what happened before.

A general-purpose game engine gives you none of that. It gives you generic parts — game objects, physics, scripting glue, a UI toolkit — and leaves you to assemble a genre by hand. The result is that most of your project becomes plumbing: wiring clicks to callbacks, syncing what a character says with the animation on screen, saving a pile of variables, rebuilding a menu every time a score changes.

advc makes those ideas language constructs. A scene is a file. A character is a line. A choice is a block. An inventory item is a declaration. Because the compiler understands the domain, it understands what you mean — and what you mean wrong:

  • A misspelled image name is a compile error, not a broken texture at runtime.
  • A choice that names a function that doesn’t exist is caught before your game ever ships.
  • Save/load, menus, and lists that render from live data are features of the language, not packages you wire together.

And because games are written as plain text, they read like scripts. A scene file is the story it plays; a whole game diffs like a manuscript, not like a binary blob.

What you get

  • One command to build. advc compiles a folder of source files into an executable for your machine. The output is the game — nothing else ships with it.
  • State that saves itself. Every variable your game keeps is saved and loaded across sessions automatically.
  • UI that follows the story. Panels — verb bars, inventories, dialogue menus, whole gamebook pages — are declared once and update themselves when the state they show changes.
  • Testing built in. A built game can be driven from a text script: clicks, waits, screenshots, even video recordings. Your walkthrough is your end-to-end test.
  • Dialogue and voice. Spoken lines with text, per-character animation, and multiple languages are part of the language.

Getting started

Install the CLI

The advc command-line tool contains the compiler, the runtime, and the test driver — everything you need to build and play a game. Install it with one command (macOS; Apple Silicon):

$ curl -fsSL https://github.com/advc-org/advc/raw/master/install.sh | sh

The installer asks GitHub for the newest release for your architecture, unpacks both packs (the compiler and the runtime) into ~/.cache/advc/, and puts the executable in /usr/local/bin (it falls back to ~/.local/bin and prints a PATH line when it has no administrator rights). A specific version is --version 0.0.1; advc --version prints what is running.

Linux and Windows builds are planned but not shipped today.

That’s the whole toolchain: an editor, a folder, and this one binary. (If you use Zed or another editor with an LSP, install the advl-lsp language server that ships alongside it — completions and go-to-definition for .advf files.)

Your first game

A game is a single folder — the directory you run advc from. Create one and add a source file:

my-game/
├── main.advf
└── assets/            ← images and sounds live here later

main.advf is the game’s scene file; other .advf files are pulled in by the import statements inside it. Open main.advf and write:

func entry
    print "hello, adventure"

entry is the one function name with special meaning: the runtime starts there when the game runs. Build from inside the game folder:

$ cd my-game
$ advc
...
built target/debug/my-game

Then play it:

$ ./target/debug/my-game
hello, adventure

That was the compiler doing a real build: parsing your scenes, checking every name it contains, baking your assets, and linking a native executable. It takes fractions of a second, so editing and re-running is a tight loop — this is how you’ll spend most of your time.

A few things to understand from this small example:

  • The game exits when its scripts end. entry printed one line and finished. A real game’s entry starts its scenes and loops; until every running script ends, the window stays open.
  • assets/ is for images and sounds. The compiler discovers them at build time; you reference each by its file name (a room.png becomes just room in the language). The folder is optional — a text-only hello world needs none.
  • Builds land in target/. target/debug/my-game/ is the executable and its runtime assets. advc --release builds an optimized target/release/ version and packs assets into a single file — what you distribute.

Build a release

$ advc --release
built target/release/my-game

The release build packs every asset it used next to the executable, so the resulting binary plus its packed assets can be zipped and shared as-is.

Tutorial: A Cold Crime Scene

In this tutorial you rebuild the heart of A Cold Crime Scene, a miniature point-and-click adventure: detective Frank Malone arrives at a ransacked office at 1:40 a.m., pokes at the evidence with the five classic verbs — Walk to · Look at · Pick up · Talk to · Pull — and turns lamps on his evidence panel as the clues mount up.

The finished game lives in the sample repository github.com/advc-org/advc/tree/master/demos/crime-scene. There it is one room of 960×352 px in a 640×480 canvas with a follow-camera, an officer you can interrogate, rain on the windows, and a “to be continued”. We will build a working slice of it: the room, one clickable hotspot, the verb system, the bottom panel, and the clue lamps. The art (backgrounds, sprite sheets, cursor icons, the panel image) is assumed to already sit in your assets/ folder.

The room you are building:

The pieces

A point-and-click scene needs four things:

  1. Actors — the background and the invisible click-targets over it.
  2. A walkable character — positioned on a walk map, reacting to the room’s light.
  3. A verb system — a scene variable that remembers which verb is selected, and click handlers that consult it.
  4. A reactive panel — the bottom HUD that shows the verbs, the evidence, and the clue lamps, and redraws itself when state changes.

Start with a folder (a game can be split across .advf files with import; the full game keeps room geometry and voices in their own files):

crime/
├── main.advf
├── room.advf
├── panel.advf
└── assets/
    ├── room/
    │   ├── room_bg.png          ← the painted office, 960×352
    │   └── desk_papers.png      ← an invisible hotspot image
    ├── detective/det_stand_e.png, det_take_papers.png, ...
    ├── ui/panel.png, verb_walk_on.png, verb_walk_off.png, clue_lamp_on.png, ...
    └── ...

The room

Room geometry in an adventure game is wider than the window and lit unevenly, and the character should shrink as he stands further back. None of that needs code on the character: a walk map carries the floor, and inside zones carried on it scale and light anyone standing there.

The room is a background actor plus invisible hotspot images, each wired to its click handler:

// room.advf
var crime
    var verb = 0        // 0 walk · 1 look · 2 pick · 3 talk · 4 pull
    var clues = 0
    var done = 0        // set to 1 when the case is closed

func crimeScene
    actor background, pos 0 0, z 0, image 0 0 0 room_bg, enable, mouse::over false

    // An invisible hotspot: its image's solid pixels are the click target.
    actor deskPapers, pos 174 156, z 1.5, image 0 0 0 desk_papers, enable
        mouse::area "image0"
        mouse::click clickPapers

    actor detective, pos 60 340, z 3, walkat officewalk walkDetective,
        pose poseDetective, mouse::over false
        image 0 -36 -156 det_stand_e
        say::color white, say::pos 320 30
        vel 100
        enable
        inside officewalk depth scaleDetective      // the walk map drives his scale
        lipsync lips_detective

    camera::bounds 960 352      // the room is 960 px wide, the view 640
    camera::follow detective    // scroll after him, half a screen at a time

camera::follow is the half-screen scroll every LucasArts room did: walk past 4/5 of the view and the room slides. The walk map itself (assets/room/officewalk.json) is data — named rectangles over the floor — and each rect can carry numbers:

"rects": [
  {"name": "depth", "points": [0, 250, 960, 352], "args": [1.0, 1.15]},
  {"name": "lightDoor",   "points": [0, 250, 115, 352],  "args": [0.36, 0.35, 0.39]},
  {"name": "lightWindow", "points": [115, 250, 350, 352], "args": [0.68, 0.39, 0.44]}
]

An inside command runs a function every frame the actor stands in the rect, passing where he is (as 0..1 across and down the rect) and the rect’s first three numbers. Depth and light are then one line each:

// $1 $2 = position across / down the rect (0..1); $3 $4 $5 = the rect's args.
func scaleDetective
    $scale = 1 + ((1.15 - 1) * $2), scale $scale

func lightDetective
    tint $3 $4 $5 600ms

tint multiplies the actor’s colours in linear light — it is the room’s lighting; the 600ms fade means walking between zones blends instead of pops. Asking for a tint that is already fading changes nothing, so an inside function firing every frame is safe.

The verb system

The game remembers the selected verb in a scene variable, set by the panel’s verb images (below). The hotspots switch behavior on it.

Here is the whole SCUMM loop for one hotspot. Note the shape, because you will write it a dozen times in a real game: the click handler cannot wait, so it only starts a function; the started thread does the work and is free to wait.

func clickPapers
    start usePapers          // click handlers can't wait: just start

func usePapers
    mouse::active false      // hold the world while we act
    switch crime::verb       // dispatch on the selected verb
        call goPapers        //   0: walk there and stand
        call Look_Papers
        call Pick_Papers
        call cantTalk        //   3: "I don't think it talks."
        call cantPull
    end
    call actionDone          // verb back to 0, mouse freed, finale when done

func goPapers
    select detective
    wait walkto 196 274      // walk to the desk, then face it
    call faceNorth

func Pick_Papers
    call goPapers
    select detective
    sound sfx_paper 0.7
    wait play det_take_papers 1 1.2s     // the take animation
    wait talk FrankTakesThePapers        // a voice line
    call gotPapers

wait play …, wait talk … and wait walkto … park the function until the thing finishes — the sequence reads top to bottom like a script.

The panel

The bottom bar is one non-modal ui block: clicking it never blocks the world, a miss falls through to the actors beneath. Its five verb images pick their “on”/“off” texture from crime::verb and its hover state, the evidence tray is a grid fed by the engine’s inventory, and the three lamps are conditions.

ui panel modal=false
    image panel pos=0,352

    // The WALK TO verb: highlighted when selected (0) or hovered.
    image pos=12,376 hit=rect click=verbWalk
        source
            switch crime::verb crime::pointing
                0 _, _ 0
                    verb_walk_on            // selected → lit
                _ _
                    verb_walk_off
        when
            mouse_enter
                crime::pointing = 0         // hover lights the verb
            mouse_leave
                crime::pointing = 5         // and stops lighting it

    // The evidence tray: whatever the player holds, in pickup order.
    grid items=$inventoryItems cols=3 size=68,42 padding=6 pos=243,373
        image $item.image hit=rect click=clickEvidence

    // One lamp per clue; they light themselves as clues mount up.
    if crime::clues >= 1 pos=534,446
        image clue_lamp_on
    if crime::clues >= 2 pos=564,446
        image clue_lamp_on
    if crime::clues >= 3 pos=594,446
        image clue_lamp_on

Nothing here is redrawn by a function. When Pick_Papers runs inventory::add papers, the tray gains a row. When a clue is counted, a lamp lights. The panel is declared once and follows the variables.

The clue counter shows an important idiom. Expressions in this language can read $-arguments and locals, but a scene variable cannot be read inside an arithmetic expression — so counting to three is a switch, one arm per value:

func gotPapers
    inventory::add papers
    call addClue

func addClue
    sound sfx_clue 0.6
    switch crime::clues          // switch reads a variable fine
        crime::clues = 1         // there were 0 clues
        crime::clues = 2         //   1 clue
        crime::clues = 3         //   2 clues
    end

func actionDone
    crime::verb = 0
    mouse::active true
    switch crime::done
        crime::done = 0
        // arm 1: the last clue was found — roll the finale
        start finale
    end

Tutorial: Vault of the King’s Relic

Vault of the King’s Relic is a gamebook in the old Lone Wolf / Fighting Fantasy sense: the screen is an open book on a desk. A numbered section of prose types onto the parchment, an illustration moves on the right, and a “WHAT DO YOU DO?” box offers numbered choices — TURN TO 54. You carry STAMINA (ten hearts), SKILL, and whatever you pick up; two dice settle the skeleton fight; fifteen sections lead from the ruined keep to a dragon’s lair and a knighthood — or a death page, which lets you step back through the book.

The finished game lives in the sample repository github.com/advc-org/advc/tree/master/demos/king-relic. Here you build its core: one page, the shared page furniture, the page-turn machinery, and the choices. The book art (parchment, choice bars, dice faces, illustrations) is assumed to be in assets/.

The book you are building:

The idea: pages are ui blocks

A gamebook is a state machine wearing a costume. State = which page is open, how much of its text has typed in, and the hero’s stats. Every page is a ui block: it appears when the state points at it, and the state is just scene variables.

// gate.advf — page #7 of the book

str n7
    en "7"
str t7
    en "The Dungeon Gate"
str p7a
    en "Dusk finds you at the ruined keep. Ivy chokes its broken towers."
str c7a
    en "Descend into the dungeon."

ui p7 modal=false
    $pageHead section=n7 title=t7        // ← the shared header, see below
    if book::reveal >= 2 pos=500,189
        text p7a width=640 outline=0 tint=0.034,0.016,0.007,1
    if book::reveal >= 6 pos=500,357
        text p7d width=640 outline=0 tint=0.034,0.016,0.007,1
    if book::reveal >= 99                // the choices box, last
        $choicesBox
        $choiceBar bar=choice_1 barOn=choice_1_on choice=c7a go=goDescend
            turn=turn23 pos=500,838

Look at the two mechanisms, because they are the whole gamebook idiom:

  • if book::reveal >= k gates every row of prose. revealText bumps book::reveal from 1 upward, seventy milliseconds apart, and the paragraph types itself on line by line — no code redraws the page, the block follows the number.
  • $pageHead and $choiceBar are components: ui blocks declared once, inlined into any page that lists them as a $-slot line, with that page’s key=value arguments bound to their parameters. Fifteen pages share one header, one choices box, one choice button.
// book.advf — the shared chrome

ui pageHead $section $title modal=false
    if book::reveal >= 1
        text $section pos=1047,41 width=240 align=center tint=0.95,0.75,0.4,1
        text $title  pos=455,119 width=695 align=center outline=0
            tint=0.13,0.011,0.005,1

// A choice button: bar art, hover art, the choice text, the func to run,
// and an optional page number to display.
ui choiceBar $bar $barOn $choice $go $turn? modal=false
    button $bar click=$go hover=$barOn
        text $choice pos=100,19 tint=1,0.95,0.85,1
        text $turn??? pos=565,19 tint=1,0.8,0.35,1

$turn? is an optional parameter: every call must bind it, and turn=none means “no page number”. The ??? mark means drop the whole element if there is no value — so a page-choice with a number shows it, and a special choice (“Open the book”) simply renders without one.

The page turn

Turning a page is the book’s heart: lock the mouse, play the curl, fade out, close the old page, open the new one, fade in, reveal the text, show the choices.

func to7
    call turnPage
    call closePages        // hide every open page, empty the scene actors
    call show7             // illustration, map flag, music, `ui::show p7 z=7`
    call openPage          // fadeIn, revealText, showChoices

func turnPage
    mouse::active false
    book::reveal = 0       // the new page starts blank
    sound sfx_page 0.8
    select curl
    play curlTurn 1 0.45s  // the 4-frame page curl
    call fadeOut           // 4 stacked quads, 60 ms a step

func revealText
    book::reveal = 1       // title
    wait nothing 160ms
    book::reveal = 2       // …as this climbs, the if-rows light up in order
    wait nothing 70ms
    // …
    call showChoices

func showChoices
    book::reveal = 99      // the `if book::reveal >= 99` row shows the box
    mouse::active true

And the state transition behind the choice — this page’s number depends on what the player has already done:

func goDescend
    mouse::active false
    switch quest::skeleton
        start to23         // haven't fought the skeleton yet
        start to61         // already fought it — different section number
    end

The page flow closes with closePages hiding every p<N> block and clearing the shared actors — one function all fifteen pages reuse.

Dice on the page

A gamebook round is: roll two dice for you, two for the foe, compare totals plus SKILL. The book tumbles the dice and settles the round with weighted randomness:

func skeletonRound
    combat::result = 0
    wait random                     // two hits in three — the arms repeat
        call hitA
        call hitA
        call missA
    end
    select spr1
    switch combat::foeHp            // foe down to 0? it falls apart; else idle
        call skeletonDies
        call skelIdleLoop
    end
    mouse::active true

func hitA
    call tumble                     // the two dice spin
    call faces54                    // set both dice to a (5,4) outcome
    combat::heroRoll = 17
    combat::foeRoll = 12
    call strikeSkeleton

func faces54                        // image names are checked at compile time,
    select die1                     // so each outcome is its own function
    image 0 0 0 die_5
    select die2
    image 0 0 0 die_4

wait random runs one arm and parks until it finishes. Because image names must exist in assets/ (the compiler checks every one), a dice face cannot be chosen from a variable — each face-pair is its own tiny function. This pattern comes up all over game-like code: where a general-purpose language reaches for dynamic naming, advc asks for the plain spelling, and the compiler keeps you honest.

The HUD that runs itself

The side bars are reactive too. STAMINA is a number — as text plus ten hearts:

ui hud modal=false
    if hero::hp >= 10 pos=290,279
        text hero::hp tint=1,0.92,0.78,1
    if hero::hp < 10 pos=304,279
        text hero::hp               // a `text <path>` renders the live value
    image heart_empty pos=52,338
    if hero::hp >= 1 pos=52,338
        image heart_full
    if hero::hp >= 2 pos=86,338
        image heart_full
    // … one if-row per heart …

hurt1 and heal1 step hero::hp by one (a switch ladder, since expressions can’t read the variable back); the hearts follow. Nothing in the HUD is written more than once.

Try the slice

func entry
    call resetGame       // every var written once, in one place
    call setupActors     // book, scene, sprites, hidden fader/flash/curl
    ui::show hud z=8
    call showCover       // the cover page: "Open the book", a new game

With a walkthrough.play script (see Testing), the fight plays itself: click ui choice_1, wait var combat::result == 1, screenshots of every section — the book is its own regression test.

Tutorial: Love Is Near

Love Is Near is a visual novel with a life-simulation loop: you are Kai, 19, one week in the harbour city of Kaminato. Mornings you sit in class; afternoons and evenings you pick from a weekly planner — the Moonbean Café (where Luna works) or chores, library, home — earning money and affection, and on Saturday the Star Festival settles one of four endings on the week.

The finished game lives in the sample repository github.com/advc-org/advc/tree/master/demos/love-is-near. Here you build two of its centerpiece pieces: the activity planner — a screen of cards that grey themselves out when you can’t afford them — and the café scene, where dialogue is played line by line. The art (backgrounds, character sprites, the dialogue box, card images) is assumed to be in assets/.

The planner you are building:

A visual novel in advc

An advc visual novel is a stack of ui layers over a painted background:

func entry
    call resetGame
    // Every layer is shown once, at an explicit z. Higher z draws on top.
    ui::show clicker z=1      // a fullscreen "click anywhere" plate
    ui::show box     z=2      // the dialogue box, name plate, arrow
    ui::show hud     z=3      // day, money, Luna's hearts, study books
    ui::show planner z=4
    ui::show toast   z=5
    ui::show sCafe   z=4.5
    call showTitle

The clicker is a trick worth knowing: a full-screen quad with a click handler is how “click anywhere to advance” is written:

// vn.advf
ui clicker modal=false
    quad color=0,0,0,0 pos=0,0 size=1920,1080 click=advance

func advance
    dlg::next = 1

A click anywhere writes a variable; the dialogue scripts wait on it.

Dialogue: one block per scene

Every line of dialogue is a str (localized text), rendered by the scene’s ui block, one if-row per line number. The block shows whichever line the variable points at, and follows it instantly when it changes:

// cafe.advf
str caf101a
    en "The door bell rings. Inside, the cafe smells of cinnamon."
str caf102a
    en "Welcome! First time here? What can I get for you?"
str c1b
    en "What do you recommend?"

ui sCafe modal=false
    if dlg::line == 101
        text caf101a pos=252,827 width=1440 tint=0.78,0.86,1,1   // narration, blue
    if dlg::line == 102
        text caf102a pos=252,827 width=1440 tint=1,0.96,0.9,1    // Luna, cream
    if dlg::menu == 1     // choice menus show clickable options on the right
        text c1b pos=1256,399 click=pick2

A text draws width= wrapped, and tint= colors it — narration in blue, speakers in their own colour.

Playing a line means: set dlg::line (the block swaps the text), then wait for the player’s click:

// vn.advf
func next                    // wait for the player (or AUTO / SKIP)
    dlg::next = 0
    vn::ctc = 1              // the click-to-continue arrow appears
    switch vn::auto
        wait var::when dlg::next == 1     // until a click anywhere
        wait nothing 2600ms               // AUTO mode
        wait nothing 70ms                 // SKIP mode
    end
    vn::ctc = 0

wait var::when <path> == <n> parks the script until the variable matches — this one line is the pump under the whole genre.

The planner

The planner shows your options as cards: Café (costs $5, +affection), Chores (+$15), Library (+study), Home. One reusable card component draws every card; go=none versions grey out when the option is unavailable.

// planner.advf
// A planner card. An absent $go renders the "off" art and the $note line
// instead of the $sub line — the greyed-out look.
ui card $art $artOn $artOff $title $fx $sub? $note? $go? modal=false
    if $go?
        button $art hover=$artOn click=$go
        text $title pos=0,303 width=420 align=center size=40 outline=0
        text $fx    pos=0,369 width=420 align=center size=34 outline=0
        text $sub??? pos=0,426 width=420 align=center size=26 font=nunito

    if $go? == false
        image $artOff
        text $title pos=0,303 width=420 align=center size=40 outline=0
            tint=0.305,0.287,0.262,1
        text $note??? pos=0,426 width=420 align=center size=26

Inside, if $go? asks whether the parameter has a value; narrowing means the plain $go is usable as the click target. Two optional parameter marks do this work: ??? skips the whole element when the parameter is none, and a plain $p after the test is narrowed to a value.

The planner block lists the cards. Since the player’s money and the day’s slot are variables, the card set composes itself from conditions:

ui planner modal=false
    if vn::plan == 1
        image plan_plate pos=580,120
        if day::slot == 1 pos=580,141
            text planAfternoon width=760 align=center size=40 outline=0
        if money::units == 0
            $card art=card_cafe artOn=card_cafe_on artOff=card_cafe_off
                title=cardCafe fx=cardCafeFx sub=none note=cardNoMoney go=none
                pos=240,240
        if money::units >= 1
            $card art=card_cafe artOn=card_cafe_on artOff=card_cafe_off
                title=cardCafe fx=cardCafeFx sub=cardCafeSub go=planCafe
                pos=240,240
        if day::slot == 1
            $card art=card_chores … go=planChores pos=750,240
            $card art=card_library … go=planLibrary pos=1260,240

That’s the game’s economy made visible in eight lines: café always available (greyed if broke), chores only in the afternoon slot, and so on.

Choosing a card writes the pick and frees the waiting plan thread:

func planCafe
    dlg::pick = 1

Reference: language basics

This page defines the shape of the language: the files a game is made of, the lexical rules, values, expressions, $ references and the reserved words. Every other Reference page builds on it. Throughout, snippets show something the compiler rejects, and the exact error it prints — all of these are pinned down by end-to-end test games (each error example names its test).

Files

A game is one folder. advc compiles main.advf plus every file an import pulls in, and discovers the assets/ directory next to it:

my-game/
├── main.advf
├── more-scenes.advf      ← pulled in by an `import` line in main.advf
└── assets/
    ├── room_bg.png
    ├── footstep.wav
    └── fell.ttf          ← fonts, if the game uses them

Images, sounds, fonts and walk maps are referenced by their stem — the file name without its extension, room_bg not room_bg.png.

Run the compiler from the game folder:

advc                 # debug build → target/debug/<game-name>
advc --release       # optimized build → target/release/<game-name>

Lexical rules

  • Indentation is significant. Children are indented 4 literal spaces past their parent; a block closes with a line at its own indent — either end or the next item at the same level.
  • Comments start with // and run to the end of the line. They take place only on their own line (in bodies, between items, and even just before an end). Any Unicode text is welcome in them.
  • Identifiers start with a letter or $, then letters, digits and _. A $name lexes as one whole identifier. Casing is not enforced; snake_case is the convention.
  • Numbers are optional-sign decimal digits with an optional fraction: 35, 0.2, -4. No scientific notation.
  • Durations are a number and a suffix: 1s, 250ms, 2min, 1h, 500us, 100ns. 0s is legal and — in animation playback — means instantly.

Strings

Strings are double-quoted. Escapes: \", \\, \n and \u{XXXX} (1–6 hex digits, any Unicode scalar value):

print "she said \"hallo\"\nnext"
print "café = \u{00E9}"

Any other escape fails the build:

// print "bad \q escape"

error: invalid string escape
--> main.advf:7
 5:
 6: func entry
 7:     print "bad \q escape"
                   ^^ unknown escape sequence `\q` (only `\"`, `\\`, `\n` and `\u{…}` are valid)

(end-to-end test: tests/blocks/utf8-escapes-bad)

A " cannot otherwise appear inside a string; \\" is a backslash followed by a closing quote.

The built-in commands

The commands of the engine (print, play, camera::pan, …) are declared with the same cmd syntax, with the type of each argument — the language is specified in the language:

    signal finished

Types are covered below; signal finished marks commands that finish (see Signals). A game file never needs to write cmd; the built-in declarations are always in effect.

Expressions

Assignments take a full expression with + - * / and parentheses:

$scale = 1 + ((1.15 - 1) * $2)
book::reveal = 0

The right-hand side of = reads numbers, durations, strings, booleans, $-references and variable paths. Everything else — command arguments, switch selectors, anim frame durations — takes a single value: no arithmetic inside a command. Compute first, then pass:

$half = 480 / 2
mouse::icon obj_105_000 obj_105_001 $half 25

A variable path inside a larger arithmetic expression (if crime::clues + 1 == 3) is not supported — comparison operands must be the path alone; compute into a $ local first.

$ references

$1, $2, … are the values passed to a running script — by start/call arguments, walk and click callbacks, inside reactions, verb grids. $name is a local you bind yourself:

func scaleDetective        // an `inside` callback: $1 $2 = position in the rect
    $scale = 1 + ((1.15 - 1) * $2), scale $scale

func f
    $half = 480 / 2        // a local, readable anywhere in this func
    start goPage $half 7   // …and passable on: `goPage` reads it as $1

Rules:

  • A $ reference is checked by its roles: if a function reads $1 via play $1 and again via image 0 0 0 $1, one value cannot be both an animation and an image, and every call site is rejected:
error: 3 `start`/`call` argument problems
--> main.advf:10
 8: func f
 9:     play $1
10:     image 0 0 0 $1
                    ^^ `$1` is used as both an anim and an image in `f`
...
--> main.advf:6
 5: func entry
 6:     start f someAnim
               ^^^^^^^^ `f` reads `$1` as an anim: no anim `someAnim`

(test: tests/blocks/start-bad-conflict)

  • The number of values a function reads is the number its callers must pass:
error: `f` reads `$2`; this call passes 1 value(s)

error: `f` reads only `$1..$1`; this call passes 2

(tests: tests/blocks/start-bad-few, start-bad-many)

  • A value bound by a caller is checked against what the callee does with it:
error: `f` reads `$1` as a func: no `func lblA`

(test: tests/blocks/start-bad-func — and start-bad-image, which offers not in assets/, did you mean `verb_look_off`? for a typo’d image stem)

  • A quoted string is never a value on such a path:
error: `str` values are looked up by name; quoted text shows nothing — declare `str <name>` with this text and pass its name

Reading compiler errors

Errors point at the source:

error: `z` value out of range
--> main.advf:4
 2: // must be rejected at compile time with an annotated error, not silently skipped.
 3: func entry
 4:     z 10
         ^^ `z 10` is out of range

(test: tests/blocks/z-out-of-range)

One offending program can produce several problems at once, counted in the title (error: 3 start/call argument problems, error: 2 unknown images); each gets its own --> location. Suggestions (“did you mean …”) come from the names the game actually has — assets, strs, funcs, ui blocks and parameters are all cross-checked.

Reserved words

  • none — the empty value of an optional ui parameter ([Reactive UI(../reactive-ui.md#optional-parameters)). Nothing may be named none — not a str, func, actor, anim, ui block, collection, inventory item, nor an asset stem:
error: str `none` is reserved (the empty value of an optional parameter)
        ^^^^ `none` is reserved (the empty value of an optional parameter) — rename this str

  • true / false — boolean literals.
  • end — block terminator.
  • when — starts a signal-handler block after a command.
  • $item, $verbs, $options, $inventoryItems — engine-bound names inside ui blocks; a parameter may not take them:
error: `ui page`: `$item` names an engine binding
        $item is an engine binding (`$item.*`, `items=$verbs` …); pick another name

Reference: top-level items

The declarations a game file is built from. Language basics lists them all in one table; this chapter gives each one’s exact syntax and rules.

import — pulling in another file

import panel
import scene/room
import ../voices
  • A bare name imports the sibling file <name>.advf; with / it is a folder path relative to the importing file; with ../ it reaches the parent folder.
  • The imported file’s items (funcs, vars, ui blocks, …) join the game; an import declares nothing by itself.
  • Imports are followed recursively; a cycle stops the build.

var — the game’s state

var crime
    var verb = 0        // 0 walk · 1 look · 2 pick · 3 talk · 4 pull
    var clues = 0
var player
    var money = 25
    var trust = 0
  • A var tree is declared once; children nest by indentation and are reached anywhere in the game by their :: path: crime::verb, player::money.
  • A variable holds an integer.
  • Two ways to write:
crime::verb = 2                  // assignment statement in a script
var::set crime::verb 2           // the command form (same write)

A variable read is what makes the game reactive — every [ui(../reactive-ui.md) condition, switch and var::when names paths and is kept up to date against them. All state — including open menus and started-but-unfinished scripts — is saved and loaded across sessions automatically (see Testing).

verb — declaring interaction verbs

verb Look
verb Pick
verb TalkTo

The engine prelude declares Look, Pick and TalkTo; a game can declare more (verb Pull, verb Close). A verb’s name appears in the $verbs grid [source(../reactive-ui.md#grid–a-list-of-items) and — when a verb-item on an actor is clicked — the engine runs the function named <Verb>_<Actor>; the menu label is <lowercased verb><Actor>. Which actor answers to which verb is decided by enableVerbs <Verb>… on the actor (Actors).

str — localized text

str t7
    en "The Dungeon Gate"
str p7a
    en "Dusk finds you at the ruined keep. Ivy chokes its broken towers."

A str is text the player reads, carried in one name: the block’s children are <culture> "<text>" lines (en first — it is the base culture; a game may carry more). Referenced by name — from a ui text element, an option menu item, or as a $ value — the culture’s text is shown.

Because strs are values that cross calls, quoted text cannot stand in for one:

error: `str` values are looked up by name; quoted text shows nothing — declare `str <name>` with this text and pass its name

The compiler scans every string in the game (quoted literals and str blocks) for its non-ASCII characters and baked fonts carry exactly those glyphs — see Assets & fonts.

default resolution / default window

default resolution 640 480    // the virtual canvas the game draws on
default window 1280 960       // the OS window opens at this many pixels

Each may be declared at most once. Both take two positive integers within 1..=8192:

error: `default resolution` values must be positive integers (1..=8192)

(test: tests/blocks/default-resolution-bad)

The window letterboxes the canvas with whole-number scaling (so pixels stay square); clicks map through that scaling back to canvas points.

inventory — items the player can hold

inventory
    magnifier inv_magnifier
    papers inv_papers

inventory
    magnifier inv_magnifier
    papers inv_papers

Each line is <name> [<iconImage>] [click=<func>]. The engine prelude provides the held set (always ordered by pickup):

  • inventory::add <item> — the player now holds <item> (an undeclared name is added on the fly).
  • inventory::remove <item> — an item the player no longer holds (a not-held item is a no-op). The declared record (name/icon) stays, so a later inventory::add appends the item at the end.
  • inventory::clear — drop every held item at once.
  • the held state is readable in any condition as inventory::<item> — a bool the engine writes through the commands (if inventory::key, a ui block’s if inventory::papers pos=… panel, wait var in a test script). Only declared items are readable; inventory::add of an undeclared name (the lazy form above) has no inventory::<name> bool.
  • a [grid(../reactive-ui.md#grid–a-list-of-items) with items=$inventoryItems renders the held items; $item.image is the icon; $item.callback is the item’s click=<func>; a template click gets $2 = the item’s declaration index.

Adding an item already held keeps its place in the order; removing one leaves the others in place (a re-add appends at the end).

collection — a named list

collection actions
    item "WALK" verbWalk
    item "LOOK" verbLook icon=icon_look

ui verbMenu
    grid items=$actions cols=1 anchor=bottom padding=10
        text $item.label click=$item.callback

collection <name>
    item "<label>" <callbackFunc> [icon=<image>]

A collection is a script-declared list: each item carries a quoted label, the function run on its click, and an optional icon image. It feeds a grid rendered with items=$<collection>; $item.label, $item.callback and $item.image bind inside the template. Values passed into a grid are also checked kind by kind:

error: `ui::show tplUI`: expects a collection, got a name

(test: tests/ui/ui-bad-arg-collection)

ui — reactive panels

ui panel modal=false
    …elements…

A ui block declares a panel of images, text, buttons and grids that re-renders itself when the variables it reads change, and is opened and closed from scripts with ui::show / ui::hide / ui::modal. The complete specification — elements, attributes, parameters and components — is the [next chapter(../reactive-ui.md).

Reference: control flow

A func is a script: an ordered list of commands the game runs. Scripts compose with four block kinds, wait or branch with keywords, and react to events with when. This chapter is the complete specification of that machinery.

The runtime model

  • The game starts at func entry (see Getting started).
  • start <func> runs a script on its own, without waiting — the script that started it continues past the line.
  • call <func> runs a script and waits for it to end.
  • The game closes when every running script has finished. A music loop or an ambient rain sound keeps the game alive: keep one running, or put the main flow itself in a script that waits for the player.
func entry
    start musicLoop        // plays forever; keeps the game alive
    call intro             // runs to completion before we go on
    call title

Passing values

Both start and call take positional values after the function name — a number, a duration, a name, a $N, a $ local, an arithmetic $local expression. The callee reads them as $1, $2, …

func goPage
    call turnPage
    call showPage $1 $2

func go7
    start goPage 7 t7 p7a

Rules (all checked at compile time, in both directions):

  • A callee that reads $2 requires two values; one that reads $1..$1 rejects two. (tests: start-bad-few, start-bad-many)
  • The value must be of the kind the callee uses it as (start-bad-image, start-bad-func); quoted text is never a value (language-basics §$).
  • One $N cannot serve two incompatible roles in one function (start-bad-conflict — see Language basics).
  • An unknown callee is an error with a suggestion: error: no func shwo, did you mean show?
  • Scripts launched by the engine (click handlers, walk callbacks, when bodies) receive their arguments positionally and take no when:
error: `start walkDet` takes positional values, not a `when` clause
hint: `start`/`call` accept no signal handlers; put the arguments on the line after the function.

(test: start-bad-when)

wait start <func> [args…] is the waiting form of start (it parks the caller until the callee ends — the same as call).

Blocks

Blocks open with a keyword, take children indented 4 spaces, close with end at the block’s own indent. They nest freely and compose with wait.

sequence — steps in order

wait sequence
    print "a"
    nothing 500ms
    print "b"
end

Each step runs after the previous one finished (a suspending step — a nothing, a wait play, an all line — holds the next one back). A bare sequence (no wait) runs on its own and the caller continues.

all — concurrent

wait all                 // or: all nothing 1, nothing 2 end
    nothing 1
    sound door 0.5
end

Every arm starts at once; the all finishes when all arms have.

random — exactly one arm

random
    sound sound_252 0.2
    sound sound_253 0.2
    sound sound_254 0.2
end

One arm is picked; the others don’t run. (wait random also waits for that arm to finish.) Choices are reproducible in scripted play — the test harness and your own runs pin the seed with ADVC_SEED (see Testing).

switch — branch on a variable

switch crime::verb       // 0 walk · 1 look · 2 pick · 3 talk · 4 pull
    call goPapers        //   0
    call Look_Papers     //   1
    call Pick_Papers     //   2
    call cantTalk        //   3
    call cantPull        //   4
end

Arms are positional, indexed from 0. The switch runs the arm at the selector’s current value; when the arm finishes, the script continues after the switch (a start arm returns at once). The selector is one value — a path, a number, a $N — not an expression (compute into a local first). Arms may be any blocks (random/sequence inside arms is normal).

The comma rules

Comma means “sibling” in a few places and “one step” in one specific one:

WrittenMeaning
print "a", print "b" in a func bodyTwo commands, in order (newline-equivalent).
all a, b end (single-line block)Two arms of the block — exactly like two lines.
sequence a, b endTwo steps.
switch x a, b endArms 0 and 1.
a comma-line inside a multi-line blockOne child of that block: the commands run concurrently (all), and the next line waits for the group.

That last row is the one to remember — it is why a multi-line sequence with a comma’d line runs two commands simultaneously:

func entry
    print "start"
    wait sequence
        nothing 1, print "during"
        print "after"
    end
    print "end"

plays as start → during → after → end: during prints at once, during the 1-second nothing, not after it. (the pinned trace is the end-to-end test tests/blocks/comma-line)

And it is why indices count lines, not commands, in a multi-line switch:

switch 1
    print "arm0", print "arm0b"    // ← line 0: both run if the value is 0
    print "arm1", print "arm1b"    // ← line 1: the value 1 picks this line…
end                                 //   …and both commands run concurrently

wait

wait prefixes a block or a suspending command; the enclosing script parks until it finishes. Without wait, the same forms are fire-and-forget.

FormMeaning
wait all / wait sequence / wait randomrun the block as above, then resume
wait nothing 5park for the duration
wait sound x 0.5 / wait play anim 1 1spark until the sound/animation ends
wait talk linepark until the voice line ends
wait walkto 196 274park until the walk arrives
wait camera::pan 320 0 1spark until the pan ends
wait var::when crime::picked == 1park until the variable matches
wait option::showpark while the menu is up

Signals and when

Commands that finish — nothing, sound, play, talk — produce a finished signal. Attach a handler with a when clause:

nothing 7 when
    finished
        start pirateLoop
end

random                       // a block too can carry one on its end line
    sound sound_252 0.2
    sound sound_253 0.2
end when
    finished
        start shipNoises
end

when is always multi-line: signal names indented 4 under when, bodies at 8, closed by an end at the command’s indent. The finished handler runs after the command/block ends — this is how loops are built:

func shipNoises
    random
        sound sound_252 0.2
        sound sound_253 0.2
    end when
        finished
            start shipNoises        // and around it goes
    end

A sequence, switch, and any wait … form do not take when — the last already suspends the caller, and a handler on it is rejected by the compiler.

var::when — variable watchers

wait var::when <path> <op> <n> parks until the variable satisfies ==, !=, <, <=, >, >= (an unset variable reads 0; see Testing for operators in play scripts). One variable per condition is supported; the watcher survives save/load.

func plan
    dlg::picked = 0
    wait var::when dlg::picked == 1    // parked until a planner card writes it
    switch dlg::pick
        …
    end

option::show — menus

option opWhat optWhat          // a menu item: text, then its click callback
option opBye optBye
$selected = option::show       // park until the player picks one
  • option <str-name> [<callback>] queues the item (the callback runs as its wake-thread body when picked).
  • option::show shows the menu — centered, white text turning red on hover — swallows every click while open, and parks the caller.
  • $var = option::show binds the picked item’s index.
  • The player’s pick resumes the menu; a click on nothing cancels (the menu just closes).

The full pattern is one function per menu, and a loop back into it:

func officerDialog
    option opWhat optWhat
    option opBye optBye
    $picked = option::show
    // …branch, or loop back for another round…

Clicks to an open option menu work even while world clicks are switched off (mouse::active false); see Actors.

say::follow <dx> <dy>Anchor this actor’s captions to its head: each frame the line’s centre sits (dx, dy) canvas-px from the top edge of the actor’s images (x at the actor’s feet, camera-adjusted), so it follows a walking speaker and a scrolling camera. say::follow 0 -20 rides 20 px above the head. say::pos and say::follow replace each other.

tint and scale

tint <r> <g> <b> multiplies the selected actor’s colours, on every image layer: 1 leaves a channel as painted, 0.5 halves its light, above 1 brightens it. It is in linear light, like lighting — put a character in a dark corner with tint 0.4 0.4 0.45. With a duration, tint 0.7 0.4 0.45 600ms moves there from the colour now shown over that time. Asking for a colour already being faded to changes nothing — so an inside function can call tint every frame without restarting the fade.

scale <number> multiplies the actor’s rendered size around its position.

Both combine with the actor itself: they act on the currently selected actor — select <name> first (below).

Image transforms

image takes one optional trailing transform:

image <n> <dx> <dy> <image> [<transform>]

It mirrors / rotates / scales / skews that one layer’s image about its own rect center (CSS’s transform-origin default — the sprite stays anchored, only the pixels move). A directional character therefore needs its east art only; the west views re-reference it mirrored:

anim det_walk_w
    duration 1
        image 0 -36 -156 det_walk_e_0 flipx
        noimage 1
    ...

Two written forms: a bare sugar word, and a quoted chain of functions (the comma and/or space separated list composes exactly like a CSS transform list — the last function applies to the sprite’s own space first):

image 0 0 0 box flipx
image 0 0 0 box "rotate(90deg)"
image 1 244 302 bottle "rotate(20deg) translate(4px, -6px)"
image 3 60 220 sign "skewX(-12deg) scale(0.95)"
FunctionMeaning
translate(tx[, ty]) / translateX / translateYOffset in canvas px (px suffix optional)
scale(s[, sy]) / scaleX / scaleYFactor about the image center
rotate(a)Any angle, deg required
skew(ax[, ay]) / skewX / skewYShear, deg
matrix(a, b, c, d, e, f)Full affine, CSS column pairs
matrix3(a … i)A raw 3×3 — the last row included
flipx, flipy≡ scaleX(-1) / scaleY(-1)
rot45 … rot315 (45° steps)≡ rotate(NNdeg)

The layer’s hitbox follows the transform: the hit rect is the AABB of the transformed corners (flips and quarter turns stay exact; diagonals give the rotated box), and clicks still land where the pixels are. The transform is saved with the layer, so it survives save/load. Two honest caveats: rotates/skews that are not 90° multiples alias on pixel art (the sprite sampler is nearest-neighbor), and a matrix3 with a non-affine last row renders through a perspective divide — the engine shows whatever you write, but a degenerate last row (0 0 0) draws nothing and makes the image unclickable.

inside — the walk map drives behavior

A walk map (assets/<map>.json) is named rectangles over the floor, each optionally carrying numbers:

  {"name": "lightDoor",   "points": [0, 250, 115, 352],  "args": [0.36, 0.35, 0.39]},

    inside officewalk depth scaleDetective
    inside officewalk lightDoor lightDetective
    inside officewalk lightWindow lightDetective

    $scale = 1 + ((1.15 - 1) * $2), scale $scale

    tint $3 $4 $5 600ms

camera — rooms bigger than the window

Reference: animations & voice

Movement on screen is anim clips played with play; speech is voice lines played with talk (or written in place with say).

anim — a frame-by-frame clip

anim pirateShout
    duration 1
        image 0 231 226 costume_25_frame_11
    duration 1
        image 0 231 226 costume_25_frame_18
    duration 1
        image 0 231 226 costume_25_frame_11

A clip is a list of frames. Each frame opens with duration <value> and takes commands indented below — usually image/noimage on the actor’s layers, but any command is legal (a frame may select another actor, sound a step, even start something).

The duration value is either a relative weight or an absolute duration:

  • a bare number (duration 1) is a weight. One loop lasts whatever play budgets; each weight-frame holds budget × weight / (sum of all weights).
  • a Duration literal (duration 2s) is an absolute length: the frame holds exactly that long, and is excluded from the weight division — the weight frames split the remaining budget. A clip made only of absolute frames ignores play’s budget entirely and lasts the sum of its frames.
anim mixed
    duration 2s             // absolute: 2 seconds, fixed
        image 0 4 219 f0
    duration 1              // weight 1
        image 0 4 211 f1
    duration 1              // weight 1
        image 0 4 210 f2

play mixed 1 10s: the 2s frame takes its 2 seconds, the two weight frames split the remaining 8 (4 s each). (end-to-end test: tests/blocks/duration-anim)

play — playing a clip

play pirateShout 1 0.7s        // one loop of 0.7 seconds
wait play det_take_papers 1 1.2s
play guybrush_stand_sw 1 0s    // apply the whole clip instantly

play <anim> <loops> <loop_duration> — the duration is the budget for one loop (<anim> and <loops>: an animation name is a checked value; a missing clip is error: ... with the closest anim’s name offered). The animation plays in real time, so a play line is async: wait play … to park, or hang a when off the end line for the finished signal.

0s plays instantly: every frame’s commands run then and there — the idiom for applying a pose (a “stand facing south” clip) rather than animating it.

Loops: <loops> counts how many times the whole budgeted sequence repeats.

say — spoken text, unvoiced

select detective
say::color white, say::pos 320 30     // where this actor's captions draw
say "What happened here?" 2s

say <text> <duration> shows the caption near the selected actor and holds it; the actor’s say::color / say::pos sub-commands place and colour it — say::pos is a fixed position, while say::follow 0 -20 anchors the caption to the top of the actor’s images (x at its feet, camera-adjusted) so it follows a walking speaker. The setting is captured when say runs, so two actors speaking at once keep their own placement. wait say … is not a thing — park with wait nothing <duration> if you need to hold the script while it shows.

voice and talk — spoken lines

voice FrankTalksTheOfficer
    en room_voices/frank_01 "All right, let's take a look."
    before
        select detective

talk FrankTalksTheOfficer

A voice is one logical line: an optional before block (runs immediately before the line plays — typically a select so the right actor speaks it), then one <culture> <wav> "<text>" child per language. Playing it:

  • talk <voice> runs the line: the text draws as a caption, the recording plays, and lip-sync runs on the selected actor if it has a lipsync <func> binding.
  • talk produces finished — wait talk … parks until the line is done.
  • voice bodies may be split per language, and the recording per culture is looked up at build time exactly like other sounds (assets/ stems checked).

Lip-sync

lipsync <func> binds a lip-sync function onto the actor — talk runs it for the line’s visemes, $1 = the viseme index, driven from the line’s own recording at build time (no per-line sync work to do by hand). lip <n> runs the bound function manually ($1 = n) for scripted mouth movement — during a sayed line, for example.

(the detective/officer functions in the sample crime-scene game show the idiom: a lipsync func per character, and the binder on the actor: see the tutorial’s actor detective block.)

Reference: Reactive UI

A ui block is a panel the script declares once and then opens and closes by name. Its elements — images, text, buttons, grids of items — re-render on their own when the scene variables they read change. You do not redraw a verb bar each frame; you write a scene variable and the bar rebuilds itself.

This reference is the complete specification. The tutorial [A Cold Crime Scene(./tutorials/crime-scene.md) walks one of the blocks below line by line.

ui panel modal=false
    image panel pos=0,352
    image pos=12,376 hit=rect click=verbWalk
        source
            switch crime::verb crime::pointing
                0 _, _ 0
                    verb_walk_on
                _ _
                    verb_walk_off
        when
            mouse_enter
                crime::pointing = 0
            mouse_leave
                crime::pointing = 5
    grid items=$inventoryItems cols=3 size=68,42 padding=6 pos=243,373
        image $item.image hit=rect click=clickEvidence
    if crime::clues >= 1 pos=534,446
        image clue_lamp_on

Declaring and opening

ui <name> [$p $q? …] [modal=true|false]
    <elements…>

modal= defaults to true: while the block is open it swallows every click that misses its elements (a click on nothing does not fall through to the world). modal=false makes it a HUD — a miss passes through to the actors beneath. Several blocks can be open at once, and the same block can be open several times (opening an open block stacks another instance; hide first when you want replace semantics).

From a script:

WrittenEffect
ui::show <def> [args...] [z=<number>]Open a stacked, non-modal instance; the caller continues. Default layer z=9.
$id = ui::show <def> …The same open; $id binds the instance’s id.
ui::hide <expr>Close: an id closes that one instance (a dead id is a no-op); a def name closes every live instance of the block.
ui::modal <def> [args...] [z=<number>]Open a menu and park the caller until it dies: the player picks an element (its click= func runs first) or clicks outside every element (cancel). Only the menu’s own elements are picks; it closes alone, leaving any HUD open under it. Opening a modal while one is pending replaces it.
wait ui::show <def> …The same non-modal open; the caller parks until the block is built.
 
func gallery
    $idx = ui::show pageX label=lblX1 cb=onX
    ui::show pageY label=lblY
    ui::hide $idx          // pageX closes; pageY (stacked above) stays

The z= draw layer orders blocks among actors: z values are the same scale as actors’ z (Actors); a clickable actor above a HUD (z higher than the block’s) takes the clicks that land on itself, and a click beside it reaches the block. A block’s text labels always draw after every image. The ESC pause menu (ui optionsMenu — see [Testing(./testing.md)) is always on top.

An instance’s body is built once, top to bottom, before the next click reaches it; the elements’ variable subscriptions keep it current for its lifetime — the build never re-runs. ui::hide <expr> is typed about it:

A ui body is element statements — image, text, button, quad, grid, expand, row, column, if, switch, $slot — and comments. Anything else is rejected at compile time, pointing at the line:

Everything over time arrives through the elements’ reactive subscriptions — the build never waits, never reads the world mid-flight.

Elements

An element is one line with attributes after it (pos=12,376, hit=rect, click=verbWalk, …). Containers take an indented body of further elements.

image — a picture

image panel pos=0,352                       // static: a named texture
image pos=12,376 hit=rect click=verbWalk    // switched: a `source` child
    source
        switch crime::verb
            1
                verb_look_on
            _
                verb_look_off

  • Switched: an image with no source and a source child picks the texture by pattern — Switched images below.

A reactive image source cannot name a scene variable:

text — a string

text hudLbl pos=20,80 click=onHud     // a `str` declaration's text
text sv::score pos=20,50              // a scene variable's live value

Two forms:

  • Bound — text <str-name>: renders a declared str.
  • Reactive — text <path>: renders the variable’s live integer value in decimal; the label follows every write.

A text may carry click= — with it, hover_tint= colours the label while the cursor is over it, and plain text keeps its colour when not clickable.

pos= is the top-left of the line box: capitals start a few pixels under y, and wrapped lines advance by the font’s line height.

row pos=20,20
    image …

if / switch — reactive containers

    image clue_lamp_on

Children render only while the condition holds; absent otherwise (a click on the spot falls through — for a non-modal block — to the world).

Conditions compare scene variables (or a literal) with ==, !=, <, <=, >, >=, combined with && and || and parentheses:

if $a? == false && $b? == false
    quad pos=0,0 size=4,4
if $b? == false && hero::key == 1
    image hero_key

A scene-variable path must be a comparison operand by itself — a variable inside a larger arithmetic expression is not supported; compute into a $ local first. $-references other than presence tests are rejected:

        conditions may only read scene variables (not `$name`/`$N`)

(test: ui-bad-opt-in-condition and friends)

    text armB click=onArmB

Switched images

An image with a source child picks its texture by first match over a multi-variable pattern:

image pos=12,376 hit=rect click=verbWalk
    source
        switch crime::verb crime::pointing
            0 _, _ 0
                verb_walk_on
            _ _
                verb_walk_off

switch lists the variables it reads; each arm is a pattern row — one cell per variable — then the image to show. _ is the wildcard; the first matching row wins (_ _ is the default). Rows may be OR-ed with ,:

switch crime::verb
    1, 2, 3
        verb_active_on
    _
        verb_active_off

Malformed patterns are located errors — a cell count mismatch says exactly what’s off (tests: ui-bad-switch-pattern, ui-bad-switch-image):

error: `ui bad`: a `source switch crime::verb crime::pointing` arm has a
3-cell pattern row but there are 2
hint: one cell per selector, `_` for wildcard, e.g. `1 _`

when — pointer events on an image

An image may take a when child binding pointer events:

image pos=20,20 hit=rect click=onVerb
    when
        mouse_enter
            crime::pointing = 1
        mouse_leave
            crime::pointing = 0
        mouse_click
            crime::verb = 1

Three kinds: mouse_enter, mouse_leave, mouse_click. A mouse_click arm fires before the image’s click= func, so the func sees any var the arm wrote. Arm bodies:

  • Simple arm — exactly one line <path> = <integer>: a direct write, no thread cost. The verb-bar fast path above.
  • General arm — anything else (several statements, a non-assignment, a computed value): the body becomes a function the runtime starts on the event, so it can wait, say, talk — it is not cut short by a later event, and a later transition does not cancel it:
when
    mouse_enter
        crime::pointing = 1
        print "enter"
    mouse_click
        print "click"
        wait nothing 1
        print "after-wait"

General arms receive no $N (test: ui-bad-when-arm):

error: `ui x`: `when enter` arm reads `$1`
        `when` arm bodies run as a callback with no `$N` args

(the interleaving is pinned by tests/ui/ui-when-general-body)

Slots — inlining one component

A slot line is $<component> [key=value …] inside another block’s container. pos=/size=/anchor= place it like an expand (no pos= fills the parent content rect); the other key=values bind the component’s params. Values are a $-parameter of the enclosing block (forwarding) or a plain name — at layout time the slot’s children are the component’s own nodes with the substitutions applied:

ui choices $choice $go modal=false
    text $choice pos=20,80 click=$go

ui page $choice $go modal=false
    $choices choice=$choice go=$go pos=20,60

The component still works as a block of its own (ui::show choices …); when inlined, its modal= is ignored. Missing bindings, unknown components and cycles are compile errors (tests: ui-bad-slot-missing, ui-bad-slot-unknown, ui-bad-slot-cycle):

error: `ui page`: `$choices` is missing parameters
                ^^^^^^^^ inlining `ui choices` needs `go=`

error: ui b inlines itself: `$a` → `$b`
        ^^ this slot closes the cycle (`$a` → `$b`)

Slot values — expressions, tuples, paths

A slot value (and each attribute part) is a comma list of elements; every element is one of three forms, chosen so each has exactly one reading (EXPR.md §2; cmd 1 -2 stays two args):

  • a bare atom — a number (6, -2), a name or ::-path, a $-reference, none, true/false;
  • a parenthesized expression — (page + 1), (1 - 2) — free whitespace inside the parens;
  • a whitespace-free compound — 1+2, $v*2, (3*2),419.

Whitespace is what separates one value from the next, so a compound containing whitespace must be parenthesized: pos=1 - 2 errors where pos=1-2 is subtraction and pos=1,-2 is the two-part tuple (test: ui-bad-slot-compound-space). A trailing comma errors, and a comma before another = is the located “separate the bindings with spaces” error.

What binds where — the kind decides, and where the parameter is read decides whether the value may be live:

Kind (from the body)Slot value formsWhere its value lands
intAny numeric element, incl. a ::-pathA condition operand: live — the value splices into each inline instance’s pred_N
numberA compile-time constant element (literals/arithmetic)An attribute part (or whole attribute); no runtime layout exists
pathA bare ::-joined scene path onlyA selector; the path inlines, so subscriptions stay static
strA str-table name, or a bare ::-path for text $p (live re-render)Text content
image / func / collectionThe nameThe asset/func/collection
  • if page >= $step reads the parameter by substitution: each $para step=… slot inlines its own value, each instance gets its own pred_N — a constant bakes into it, a ::-path expression (step=(scene::page + 1)) re-evaluates when the var writes (tests: ui-cond-param, ui-cond-param-live). A def whose conditions read parameters compiles because it is opened somewhere (ui::show) or only ever inlined; a condition parameter cannot be bound at an open site — that open arg is a runtime value (test: ui-bad-cond-param-opened).
  • tint=$ink (the whole-attribute form, from the slot’s tuple ink=0.95,0.75,0.4,1) and per-part forms (pos=500,$y, pos=(4*2),419) resolve at compile time per instance (test: ui-slot-attr-params); a scene variable bound into an attribute is the runtime-restyle error — R11 territory (test: ui-bad-attr-live-scene-var) — as is a wrong-arity tuple (test: ui-bad-attr-tuple-arity).
  • text $hp (a str-kind parameter) still takes the str-table name, and now the bare path too: hp=sv::hp inlines the path and the label re-renders live wherever the stat is inlined (test: ui-stat-hud). switch $sel reads the slot’s ::-path the same way (test: ui-param-switch).
  • A $-parameter inside a slot value’s expression or a forward into an int/number/path parameter is a runtime value: an error (test: ui-bad-slot-runtime-param) — runtime parameters reach a component’s predicates and layout at R11.
  • A bool-valued element (true, or a comparison) is never a slot value — bools are the 1/0 of conditions, not values (test: ui-bad-slot-bool).
  • font=$f reads the slot’s font stem: the value is checked against the font assets (not the str table), and the resolved stem lands in the label’s per-instance font segment (test: ui-param-font-slot); an open binding stays rejected — the runtime resolves fonts by name only at build time (test: ui-bad-param-font).
  • An optional parameter bound a value everywhere (a numeric element or a tuple counts) draws the usual “its ? is pointless” warning (test: ui-opt-warn-num).

Optional parameters

Declare a parameter optional with a trailing ?. Every call still binds it — an optional parameter is passed none, never left out:

ui choiceBar $bar $barOn $choice $go $turn? modal=false
    button $bar click=$go hover=$barOn
        text $choice pos=100,19 tint=1,0.95,0.85,1
        text $turn??? pos=565,19 tint=1,0.8,0.35,1

$choiceBar bar=choice_1 barOn=choice_1_on choice=cA go=goA turn=turnA pos=500,838
$choiceBar bar=choice_2 barOn=choice_2_on choice=none go=none turn=none pos=500,926

The three marks do different work where the parameter is read:

WrittenTypeMeaning
$p?BoolA test: “has a value”. Only in an if condition or as a two-arm switch $p? selector.
$p??the valueA lift: if $p is none, whatever $p?? sits in is absent.
$p???the valueA guard: if $p is none, the line — and its indented subtree — is skipped.

What an absent value does by position:

Position$p?? absent$p??? absent
text <source>The node is removed (children remain in an expand).Node and subtree skipped.
image <source>The node and its event children removed.Skipped.
button <base>An expand with no art, hit, click or hover — text children still render.Button and children skipped.
hover= / click=The attribute is left out (the node shows, not clickable).The node is skipped.
grid items=The grid is removed (zero rows).Skipped.

Narrowing. Inside if $p? the plain $p is a value and needs no mark; arm 1 of switch $p? proves it present, arm 0 proves it absent:

ui n $go? $art? modal=false
    if $go?
        button box click=$go pos=0,0
    switch $art?
        quad pos=0,0 size=4,4 click=onNone
        image $art pos=0,0

Negation is $p? == false (there is no !).

Every misuse is an error pointing at the read (tests: ui-bad-opt-* — the whole family: ui-bad-opt-decl-marks, ui-bad-opt-mark-required, ui-bad-opt-in-func, ui-bad-opt-plain-value, ui-bad-opt-bool-value, ui-bad-opt-in-condition, ui-bad-opt-into-required, ui-bad-opt-none-required, ui-bad-opt-missing-key, ui-bad-opt-switch-arms, ui-bad-opt-reserved-none …):

error: `ui c`: `$t` may be none (it is declared `$t?`) here — it is read as a
value by `text`: test it first with `if $t?`, keep the line with `$t??`, or
skip it with `$t???`

error: `ui p`: `t=` of `ui c` is required, so it cannot be none
        ^^^^ `none` is the empty value of an optional parameter; `$t` of `ui c`
        is required, so it cannot be none — pass a value name

A pass-through warning fires when a parameter is never actually used or is redundant with an optional target (tests: ui-opt-warnings, ui-opt-warn-opens).

Click dispatch

A left click goes to the first of these that is open, topmost first:

  1. The ESC pause menu.
  2. Modal ui blocks — a ui::modal menu, or a block declared modal=true.
  3. An option::show menu (it swallows every click while up).
  4. Non-modal blocks — a miss falls through.
  5. The world: actors (highest z first), then walking to the clicked floor.

mouse::active false cuts off category 5 entirely, and the pointer stays visible (see Actors › The mouse).

Limitations

  • A scene-variable read must be the whole operand in var::when conditions (compute into a variable first) — ui if conditions read them live anywhere in the expression.
  • Per-item hover in a grid: two hoverable images in the same grid share one hover target, so mouse_enter/mouse_leave fire for the cell group rather than per item; per-item click= is unaffected.
  • Attribute parts take parameters and constant expressions; font=$f takes the slot’s font stem (verified against the font assets, and the label renders with it per inline instance), z= stays an open-argument. An open ui::show arg cannot feed an int/number/path parameter — nor a font=$p stem — those take the slot’s compile-time values.
  • An image whose texture is a string-valued variable is rejected — string variables are not yet reactive sources; use integer variables with source { switch }.
  • A click= func runs synchronously and cannot wait — use a when mouse_click general arm (which can), or have the click func start another script.

Reference: assets & fonts

Assets live in ./assets next to the game’s source files. The compiler discovers them at build time and copies each one it uses next to the produced executable, so the game runs from anywhere; the packed --release build tucks them all into one file.

Images

  • .png files in assets/ (and subfolders), referenced by stem — the file name without extension, room_bg not room_bg.png.
  • Every image name a game writes is checked against assets/ at compile time — in command arguments, ui elements, inventory icons, collection icons, and values passed through start/call:
error: unknown image `fcae`
--> main.advf:6
 4: func entry
 5:     actor face, pos 0 0, z 0, image 0 0 0 fcae, enable
                                                    ^^^^ not in assets/, did you mean `face`?

(test: tests/blocks/image-bad-name)

No image name is ever derived from another name; every one is written literally, and the compiler keeps you to the real files.

Sounds

  • .wav files, referenced by stem, in sound <stem> <volume> and as voice line recordings.
  • Same rule as images — a sound sound_252 0.2 names a real file or the build fails at that line.

Fonts

  • .ttf files, referenced by stem through the font command:
font efmi                       // the active font for text from here on
font cinzel                     // a second font, loadable per-label with font=
font fell size=48 pxrange=4     // bake-quality overrides, rarely needed
  • font <stem> [size=<px>] [pxrange=<px>] — size= and pxrange= are bake quality knobs (defaults 32 and 4); omitting them bakes exactly as before. (tests: font-bake-settings, font-bad-named-arg, font-bad-size-zero)
  • A font <stem> names a real font file, with the usual suggestion: error: unknown font fll… did you meanfell? (test: font-bad-name)
  • A font carries the glyphs the game actually uses. The compiler scans every string (quoted literals and str blocks) for non-ASCII characters and the baked font set covers ASCII plus exactly those — em dashes, curly quotes, accents, CJK, whatever the game writes. A character the font cannot shape stops the build:
error: font `efmi` is missing 1 glyph the game uses
--> main.advf:9
 7: func entry
 8:     print "中"
              ^ font `efmi` has no glyph for U+4E2D (中)

(test: font-bad-glyph)

Per-label font= in ui text elements must name a loaded font; an unloaded name is a warning and the label falls back to the active font.

Walk maps

walkat <map> <func> and inside <map> … name a JSON walk map, assets/<map>.json — named rectangles (with optional numbers) over the floor that drive walking, depth scaling and light zones; see Actors › inside.

Missing assets at runtime

The build validates names; it does not fail over unreadable files. A source file the compiler cannot read or encode is logged and skipped; at runtime the missing image draws as a 1×1 magenta placeholder and a missing sound reports, so a broken asset is loud, not a crash.

Build output

Everything generated lands in target/ in the game folder:

target/
├── debug/<game-name>    ← the debug build (default)
├── release/<game-name>  ← the --release build (assets packed into one file)
└── assets/              ← the runtime copies of what the build used

Reference: testing & scripted play

A built game can be driven from its standard input: clicks, waits, screenshots and video. A script of these lines plays the game by itself — to watch it, to record it, or as an end-to-end test. Every sample game ships a walkthrough.play that plays it completely on its own.

ADVC_STDIN=1 ./target/debug/my-game < walkthrough.play                  # in its window
ADVC_HEADLESS=1 ADVC_STDIN=1 ./target/debug/my-game < walkthrough.play  # no window, as fast as it can run

ADVC_SEED=<n> fixes the random choices (random arms, dice) so runs repeat.

How lines run

Every line goes into a queue the game runs each frame, in order. Most lines take effect at once; a wait … line holds the queue until its condition is true, so the lines after it run only then. Time is game time: nothing counts down while the game is paused, so scripted waits are reproducible however busy the machine is.

If a wait isn’t satisfied within its timeout (2 minutes unless it says timeout=…), or a click target can’t be found, the script fails: the error is printed with its line number and the game exits with status 1.

# starts a comment (a # inside quotes is text).

The pause menu

The ESC overlay is a ui block the engine ships with every game — dimmed, with three items a grid renders from the engine’s options:

ui optionsMenu
    quad color=0,0,0,0.3
    grid items=$options cols=1 anchor=center padding=20
        text $item.label click=$item.callback

save / load write and restore all dynamic state — variables, open panels, scripts parked mid-line — so a walkthrough can round-trip a save and keep playing identically.

Video

start-video <path> records the canvas at twice its size — 1280x960 for a 640x480 game — whatever the window size, at up to 60 frames a second, with the game’s sound, as an .mp4 (an existing file is replaced). Recording runs in real time with the window; stop-video, exit, a failing script or closing the window writes the file.

(echo "start-video target/run.mp4"; cat walkthrough.play) | ADVC_STDIN=1 ./target/debug/my-game

Everything drawn in the canvas is recorded.

Building with advc --release

advc --release builds the same game into target/release/, optimized, and packs every asset the game uses into one file next to the executable — the deliverable form, ready to zip and share. Behavior is identical to the debug build.
